# @ethonline2026/timeseries

TimescaleDB store for the Agentic EMS. It owns every storage concern of the
stack — hourly pool metrics, the TimesFM-3 forecast ledger, the agent's
decision audit trail, SQL-computed forecast evaluation, and a temporal vector
index the agent retrieves from — and exposes them as typed repositories over
an injectable `SqlRunner` port.

`@ethonline2026/langchain-agent` wires these in as thin tool adapters; it
never issues SQL itself.

## Why a separate package

The agent needs four different things from the same database, and each has a
different correctness story:

| Layer | Question it answers | Where the logic lives |
|---|---|---|
| Metric store | What did the pool do? | `pool_metrics_hourly` hypertable |
| Forecast ledger | What did TimesFM-3 predict, and when? | `ts_forecasts` (one row per horizon step) |
| Decision ledger | What did the agent decide, citing what? | `ts_decisions` |
| Evaluation | Was the forecast right? Did the decision beat holding? | SQL views, never application code |
| Vector index | What similar history is relevant? | `ts_embeddings` (pgvector / vectorscale) |

Two design choices carry most of the weight:

**Forecasts and actuals are both hypertable rows.** "Was the forecast right?"
is therefore a plain SQL join on `(pool_id, metric, target_ts = ts)` — not
application-side matching, and never a number the language model produces. The
`issued_at` column is the hypertable time dimension (monotonic, append-only)
while `target_ts` is an indexed value column used by the joins.

**Embeddings are only ever generated from database rows.** `serializer.ts`
renders citation-tagged text where every line carries the id of the row it
came from. Model prose never becomes an embedded document, which closes the
loop where a hallucination could otherwise become a retrievable "fact".

## Install

```bash
pnpm add @ethonline2026/timeseries
```

## Configure

Copy `.env.example` and set the DSN from the Tiger Cloud console:

```bash
TIMESERIES_DATABASE_URL=postgres://tsdbadmin:<pw>@<host>.tsdb.cloud.timescale.com:<port>/tsdb?sslmode=require
```

SSL is enabled automatically for any non-local host. Note that `pg` merges the
parsed DSN *over* the explicit config, so a leftover `sslmode` would silently
override the resolved TLS policy — the runner strips those parameters and owns
the policy itself (`require`/`prefer` encrypt without verifying, exactly as
libpq does; supply `sslrootcert` to verify for real).

The connection pool is cached on `globalThis` (serverless instances come and
go, but a warm instance reuses one pool) and defaults to `max: 5` because the
Tiger Cloud free tier caps connections.

## Migrate

```bash
pnpm --filter @ethonline2026/timeseries migrate
pnpm --filter @ethonline2026/timeseries migrate -- --vector=require
```

Hypertable and compression SQL is generated by the official
[`@timescaledb/core`](https://github.com/timescale/timescaledb-ts) builders.
Because those emit `create_hypertable(...)` without `if_not_exists`, the
migration is idempotent by **probing first** — it runs the library's own
`inspect()` query and only executes DDL when the table is not yet a
hypertable. Views use `CREATE OR REPLACE`, so a definition change always
applies on the next run.

The migration also probes `pg_available_extensions` and records what the
server actually offers into `ts_capabilities`. The vector layer is created
only when `pgvector` is present; otherwise it is skipped and
`VectorRepository` raises a typed `VectorUnavailableError` rather than the
search silently returning nothing.

## Usage

```ts
import {
  PgSqlRunner,
  TimeseriesClient,
  ForecastRepository,
  PerformanceRepository,
} from '@ethonline2026/timeseries';

const runner = PgSqlRunner.fromEnv();
const metrics = new TimeseriesClient(runner);
const forecasts = new ForecastRepository(runner);

// Category B input for TimesFM-3.
const window = await metrics.getMetricWindow(poolId, 'apy', since);

// Persist a validated run — every horizon step, all nine quantiles.
await forecasts.saveRun(run);           // runId becomes the citation anchor

// Evaluation figures come from SQL, not from the caller.
const calibration = await new PerformanceRepository(runner)
  .getCalibrationSummary(poolId, { from, to });
```

### Temporal vector retrieval

```ts
import {
  VectorRepository, VertexEmbeddingService,
  serializeMetricWindow, serializeForecastRun,
} from '@ethonline2026/timeseries';

const vectors = new VectorRepository(
  runner,
  new VertexEmbeddingService({ project: process.env.GOOGLE_CLOUD_PROJECT! }),
);

// Only ever from real rows — each chunk carries its source ids.
await vectors.upsertBatch([
  serializeMetricWindow({ poolId, metric: 'apy', points }),
  serializeForecastRun(run),
]);

const hits = await vectors.searchTemporal({ query, poolId, k: 8 });
// hits[i].sourceIds are what the agent's citation guard verifies.
```

Backfill history so the index is useful on day one (idempotent — re-running
skips chunks that are already stored):

```bash
pnpm --filter @ethonline2026/timeseries backfill:embeddings -- --days 90
pnpm --filter @ethonline2026/timeseries backfill:embeddings -- --dry-embed   # no Vertex calls
```

## Schema

All hypertables are created by the migration.

| Table / view | Time column | Compressed | Purpose |
|---|---|---|---|
| `pool_metrics_hourly` | `ts` | yes | Hourly pool metrics |
| `ts_forecasts` | `issued_at` | yes | Forecast ledger, one row per horizon step |
| `ts_decisions` | `decided_at` | yes | Decision audit trail with cited ids |
| `ts_embeddings` | `ts_start` | **no** | Temporal vector index |
| `ts_capabilities` | — | — | Capability snapshot per migration |
| `ts_forecasts_latest` | — | — | Latest stored path per (pool, metric, target) |
| `v_forecast_calibration` | — | — | Forecast joined to realized actuals |
| `v_realized_yield` | — | — | Realized APY per daily bucket |
| `v_decision_outcomes` | — | — | Each decision scored against later yield |

Two deliberate choices worth knowing:

- **`ts_embeddings` is not compressed.** ANN indexes are not maintained across
  compressed chunks, so the trade is index validity for storage. The other
  three hypertables are scanned by time, not by similarity, so they keep
  compression with a 7-day policy.
- **The ANN index flavour follows the server.** `vectorscale` present →
  `diskann`; otherwise `hnsw`. The migration probes and picks. Both use
  `vector_cosine_ops`, so scores mean the same thing either way.

## Verify

```bash
pnpm --filter @ethonline2026/timeseries test          # 91 offline tests, no network
pnpm --filter @ethonline2026/timeseries verify:live   # against a real service
```

`verify:live` migrates, asserts idempotency, writes and re-writes metrics,
persists a forecast, checks that the calibration view's pinball loss and
coverage agree with their definitions, records a decision, exercises the
vector round-trip, then deletes its probe rows. It uses a per-run pool id, so
it is safe to point at a shared service.
